# T1059.001 — why no `host_application` predicate is writable

Measured 2026-09-19, after D-055 made `host_application` reachable, to decide
between three options for the technique:

1. write the rule for `-ExecutionPolicy Restricted` (what the scenario was
   believed to have run), accepting a corpus fit;
2. change the scenario to produce `-ExecutionPolicy Bypass`, per C-05;
3. write both predicates, each documented for what it covers.

**The measurement rejects 1 and 3 and makes 2 the only option — and it rejects
them for reasons that were not the ones under discussion.**

## 1. The claim the fork rested on was mine, and it was wrong

Six documents and two commit messages said *"both scenarios ran
`-ExecutionPolicy Restricted`"*. That was never measured. It was inferred from
one screenful: `Bypass` counted 0 on `s1_v3`, and the top `host_application`
values there were `Restricted`. No row was ever joined to the attack.

**The distinct `host_application` values tell a different story.** There are
exactly **two** `Restricted` strings in the entire corpus, and they are
byte-identical on **all five collections**:

    powershell.exe -ExecutionPolicy Restricted -Command Write-Host 'Final result: 1';
    powershell.exe -ExecutionPolicy Restricted -Command $Res = 0 $InboxIMEs = (@( '{0000897b-...

Both are Windows servicing scripts — an IME inventory check and a trivial
probe. They are present on the clean hosts and the scenario hosts alike,
attributable to Windows on all of them and to an attacker on none.

`clean_c` and `s1_v3` carry only **three** distinct values in total: those two
plus bare `powershell.exe`.

## 2. `Restricted` is not a corpus fit. It is a non-discriminator

    rows whose host_application contains each token

    token        clean_a  clean_b   s1_v2  clean_c   s1_v3
    restricted        56       56      72      104     138
    bypass           640      640     460        0       0
    -enc               0        0       0        0       0
    hidden            16       16      16        0       0
    noprofile         72       72      48        0       0

`restricted` fires on every collection and fires **most** on `clean_c`, a clean
one. A rule on it would not be "fitted to this corpus at the cost of
generality" — it would fail on this corpus too, matching all five.

`bypass` is a host-1 artifact: 640/640/460 on host 1 and **zero** on host 2,
clean and scenario alike. It tracks the machine, not the behaviour. Host 1's
`Bypass` invocations are Chocolatey, VS Code and the project's own
`day1-install.ps1` / `02-clean-b.ps1` provisioning scripts — visible in the
values themselves.

**Option 3 is rejected on top of that.** A `Bypass` rule firing 640 times on
`clean_a` attributes to entities, and would place a clean-host binary at the
top of the entity table — destroying the D-058 result that *no clean collection
produces a critical binary at all*. Its `expected` would be 0 on both scenario
hosts, so the corpus cannot validate it. A rule the evidence cannot test is not
coverage that is honestly documented; it is an assertion with a note attached.

## 3. The decisive fact: the technique's own precondition never held

T1059.001 is listed in the grid as **"PowerShell *when script-block logging is
off*"**. That scoping is the whole point of the row: `evtx.ps_classic` earns
its place because it records PowerShell when `evtx.powershell` 4104 records
nothing.

    collection   4104 rows   ps_classic rows
    clean_a           982           763
    clean_b           997           770
    s1_v2           1,270           726
    clean_c           470           134
    s1_v3             644           203

**Script-block logging was ON for every collection in this corpus.** 4104 is
abundant everywhere, and on `s1_v2` it is the family that carries the attack's
own `DownloadFile` call — which is why R-ATOMIC-0003 works.

So the sub-scenario this row describes was **never exercised**. There is no
collection in which PowerShell ran with logging off, and therefore no positive
class for the technique as scoped, independent of which flag any rule might
match.

## 4. What the scenario's PowerShell actually looked like

Bare `powershell.exe`, no flags: 22/29/**149**/30/**65** rows. The scenario
hosts carry the most, and `ps_history` — the typed-command record — carries
180 commands on `s1_v2` and 90 on `s1_v3`, including the attack itself:

    Copy-Item -Path C:\Windows\System32\notepad.exe -Destination Z:\invoice_scan.exe
    Test-Path Z:\invoice_scan.exe
    python -m http.server 8000

The scenario was built and run by **typing at an interactive prompt**. An
interactive session launches as `powershell.exe` with no arguments, so
`host_application` carries no flag to match. **No flag-based predicate can
detect this scenario**, because the scenario's PowerShell had no flags.

## Decision

**Option 2.** T1059.001 stays unwritten and stays `observable-unwritten`, with
the reason corrected: not "the predicate is inverted" but

* the technique's precondition (logging off) never held in any collection;
* the scenario's PowerShell was interactive and carried no launch flags;
* neither candidate flag discriminates — `restricted` fires on all five,
  `bypass` fires on host 1 only.

This is C-05 by construction, found a second time: **the scenario must produce
the indicator the rule set is meant to detect.** A future collection that wants
this row must (a) disable script-block logging for the attack step and (b)
launch PowerShell non-interactively with the flags the rule reads. Both belong
in the C-05 checklist.

## Method note

This measurement exists because a claim was challenged, not because a test
failed. The wrong version was written into six documents and two commits before
anyone asked how it had been established. The same class as D-060, and the
reason the verification-coverage discipline was added to the defect log's
pattern section the same day: **a check that cannot fail on the thing it
claims is not evidence, and neither is a screenful read in the right
direction.**
